# Contributing to Open Governed Swarm of Agents

Thank you for your interest in contributing! This document provides guidelines for contributing to the project.

## Code of Conduct

This project adheres to the Contributor Covenant [Code of Conduct](CODE_OF_CONDUCT.md). By participating, you are expected to uphold this code.

## Getting Started

### Prerequisites

- **Node.js 20+** (required for `@napi-rs/cli` / CI; `package.json` declares `engines.node`)
- pnpm 10.30.1+ (see `packageManager` in `package.json`)
- Docker & Docker Compose (for local development)
- Rust stable (for `sgrs-core`; CI uses `dtolnay/rust-toolchain`)

### Development Setup

1. **Clone the repository**
   ```bash
   git clone https://github.com/DealExMachina/open-governed-swarm-of-agents.git
   cd open-governed-swarm-of-agents
   ```

2. **Install dependencies**
   ```bash
   pnpm install
   ```

3. **Build Rust kernel, then TypeScript**

   On a clean clone, `sgrs-core/index.js` and typings are generated by napi — run Rust **before** `tsc`:

   ```bash
   pnpm build:rust   # produces sgrs-core native addon + index.js / index.d.ts
   pnpm build        # tsc -> dist/
   ```

4. **Start database and services**
   ```bash
   docker-compose up postgres nats minio
   ```

5. **Run tests**
   ```bash
   pnpm test
   ```

6. **Start development**
   ```bash
   # In one terminal:
   pnpm swarm:start
   
   # In another:
   pnpm feed
   ```

## Making Changes

### Branch Naming

- Feature branches: `feat/description`
- Bug fixes: `fix/description`
- Refactoring: `refactor/description`
- Documentation: `docs/description`

Example: `feat/pressure-directed-activation`

### Code Style

**TypeScript:**
- Strict mode enabled (types required)
- No `any` types without explicit `// @ts-expect-error` comment
- Import statements must use `.js` extensions (ESM)
- Comments only for "why", not "what" (code should be self-documenting)

**Naming:**
- TypeScript: `camelCase` for variables/functions, `PascalCase` for types/classes
- Database: `snake_case` for table/column names
- Constants: `UPPER_SNAKE_CASE`

**Error Handling:**
- Never silent `catch` blocks
- Log all caught exceptions with context
- Re-throw unrecoverable errors
- Use `toErrorString()` from `./errors.ts` for safe serialization

**Comments:**
```typescript
// Good: explains why
const CONVERGENCE_THRESHOLD = 0.99; // Lyapunov V must drop below 1% for 3 consecutive rounds

// Bad: explains what (obvious from code)
const x = 5; // x is 5
```

### Testing Requirements

- **Unit tests**: Required for new modules and utility functions
- **Integration tests**: Required for agent loops and policy evaluation
- **Coverage target**: >60% for critical paths (agent loop, convergence, governance)

Test files live in `test/unit/` following the same structure as `src/`:

```bash
# Example test structure
test/unit/
├── db.test.ts
├── logger.test.ts
├── governance.test.ts
└── convergenceTracker.test.ts
```

**Running tests:**
```bash
pnpm test              # Run all tests
pnpm test:watch       # Watch mode
pnpm test:coverage    # Generate coverage report
```

### Pre-commit Checks

Run these before pushing:

```bash
pnpm lint              # ESLint (type-aware; needs sgrs-core typings after build:rust)
pnpm format:check      # Prettier
pnpm typecheck         # TypeScript strict check (after build:rust)
pnpm test              # Unit tests
pnpm build:rust && pnpm build   # Full compile (order matters on fresh checkouts)
```

## Submitting Changes

### Pull Request Process

1. **Create a feature branch**
   ```bash
   git checkout -b feat/your-feature
   ```

2. **Make your changes**
   - Follow code style guidelines
   - Add tests for new functionality
   - Update documentation if needed

3. **Run all checks**
   ```bash
   pnpm lint:fix
   pnpm format
   pnpm build:rust
   pnpm typecheck
   pnpm test
   pnpm build
   ```

4. **Commit with clear messages**
   ```bash
   git commit -m "feat: add pressure-directed agent activation
   
   - Implement pressure calculation from convergence history
   - Add per-dimension pressure tracking
   - Integrate with hatchery scaling decisions
   
   Fixes #123"
   ```

   Follow conventional commits:
   - `feat:` New feature
   - `fix:` Bug fix
   - `docs:` Documentation
   - `test:` Test additions
   - `refactor:` Code reorganization (no functional change)
   - `perf:` Performance improvements
   - `ci:` CI/CD changes

5. **Push and open PR**
   ```bash
   git push origin feat/your-feature
   ```

6. **PR Description**
   - Reference related issues (#123)
   - Describe what changed and why
   - Include test/validation approach
   - Link to any relevant documentation

### PR Review Checklist

Before requesting review, ensure:

- [ ] All CI checks pass (lint, test, build, security)
- [ ] Code follows style guidelines
- [ ] Tests added/updated
- [ ] Documentation updated if needed
- [ ] No merge conflicts with main
- [ ] Commit messages are clear

### Handling Review Feedback

- Respond to all comments (even to say "done")
- Avoid force-pushing unless requested
- Don't close and reopen PRs; use feedback to improve

## Documentation

### Updating Docs

- Architecture decisions: Update `/docs/ARCHITECTURE.md`
- Validation/testing: Update `/docs/validation.md`
- Configuration: Update README.md "Configuration" section
- API changes: Update `/docs/` as needed

### Writing Documentation

- Use clear, concise language
- Include code examples where relevant
- Reference related files with paths
- Update table of contents if needed

## Reporting Issues

### Bug Reports

Include:
1. **Environment**: OS, Node version, branch
2. **Steps to reproduce**: Exact steps to trigger the bug
3. **Expected behavior**: What should happen
4. **Actual behavior**: What actually happened
5. **Logs**: Relevant error messages or logs

### Feature Requests

Include:
1. **Problem statement**: What problem does this solve?
2. **Proposed solution**: How should it work?
3. **Alternatives**: Other approaches considered
4. **Additional context**: Why this matters

## Release Process

Releases follow semantic versioning (MAJOR.MINOR.PATCH):

- **MAJOR**: Breaking changes
- **MINOR**: New features (backward compatible)
- **PATCH**: Bug fixes

Releases are coordinated by maintainers. See GOVERNANCE.md for decision-making.
